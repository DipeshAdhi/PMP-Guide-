Extreme Programming (XP)

XP takes good engineering practices and turns them up to the maximum: if code review is good, review all the time (pair programming); if testing is good, test first (TDD); if integration is good, integrate many times a day. It's the most technical of the agile methods.

The 5 XP values

Communication

Everyone sits together and talks daily, including the customer.

Simplicity

Do the simplest thing that could possibly work. No speculative features.

Feedback

From tests in minutes, from the customer every iteration.

Courage

Tell the truth about progress; refactor or throw away code when needed.

Respect

For each other's work, time, and the customer's decisions.

The XP flow

Click any part of the flow. Stories feed release planning, uncertain estimates go to a spike, the team builds in short iterations, and the customer approves small, frequent releases.

The planning game

In XP the customer decides business value and priority; the developers estimate. Some stories are too uncertain to estimate, so you can run a spike (a short, timeboxed experiment), but each spike uses 1 point of the iteration. The team's velocity is 10 points. Pick the stories that deliver the most value.

Test-driven development: red → green → refactor

Write a failing test first, write just enough code to pass it, then clean up. Step through it with a real Scholar Academy function: the attendance percentage.

The 12 XP practices

Grouped the way Kent Beck's original practices usually are.

🔁 Fine-scale feedback

Pair programming: two people, one keyboard. The driver types, the navigator reviews and thinks ahead. Swap often.
Planning game: customer sets priorities, developers estimate (above).
Test-driven development: tests before code (above).
Whole team / on-site customer: a real customer sits with the team to answer questions.

🌊 Continuous process

Continuous integration: merge and run all tests many times a day.
Refactoring: improve the design without changing behavior, protected by tests.
Small releases: release to real users as often as possible.

🤝 Shared understanding

Coding standards: everyone writes code the same way.
Collective code ownership: anyone can improve any code.
Simple design: no code for features you don't need yet (YAGNI).
System metaphor: a shared story of how the system works.

💚 Programmer welfare

Sustainable pace: about 40 hours a week. Overtime two weeks in a row is a warning sign (agile principle 8).

📝 Key points to remember

  • A spike is a short, timeboxed research task to reduce uncertainty: technical spikes or functional spikes.
  • In pair programming: driver writes code, navigator reviews.
  • TDD order is always red → green → refactor.
  • XP's customer sets business value; developers give estimates. Neither does the other's job.
  • "Sustainable pace" (the 40-hour week) comes from XP and matches agile principle 8.
